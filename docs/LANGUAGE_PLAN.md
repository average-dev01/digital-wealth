# Multi-language support via DeepL (English, Arabic, French, Spanish)

## Status  complete for the customer-facing app

**Every customer-facing screen is translated into all four locales.**
`messages/{en,ar,fr,es}.json` each hold **410 keys**, verified key-for-key with
matching ICU placeholders and rich-text tags. `next build` produces 83 static
pages (4 locales x ~21 routes) with no missing-message errors.

Covered: site metadata, header/nav, footer (incl. the risk disclaimer), home,
about, security, FAQ, services, **contact, auth, forgot-password,
reset-password, and the whole dashboard**  layout/sidebar, overview, wallets
(including the deposit, withdraw and convert dialogs), transactions, KYC and
settings. Form validation messages, toasts and `aria-label`s are translated
too, not just visible copy.

Also translated: transaction types and statuses, which were previously rendered
raw from the database enum with a `capitalize` class (`common.transactionTypes`
/ `common.statuses`), and timestamps, which used a hardcoded `date-fns`
"d MMM yyyy, HH:mm"  now `useDateTimeFormat()`, an `Intl.DateTimeFormat`
pinned to `-u-nu-latn` so Arabic keeps Western digits like the `num` utility.

**The translations were written directly rather than generated by DeepL**  the
DeepL Free tier now requires a payment card, which wasn't available. Nothing in
the design depended on DeepL: the app only ever reads the JSON. The
`scripts/translate.ts` pipeline is intact and still the right tool for future
languages; `messages/.{ar,fr,es}.source.json` were seeded from `en.json`, so a
future `pnpm --filter frontend translate` run reports "up to date" and would
only translate keys added after that point, rather than overwriting this work.

**Deliberately still English:** the admin panel (per the scope decision, and
pinned `dir="ltr"`), and `app/error.tsx` / `app/global-error.tsx` /
`app/not-found.tsx`, which render above the `[locale]` segment where no locale
exists  they own their own `<html>` document for the same reason.

**Still open:** the legal and risk copy needs a native-speaker review before
production (corrections belong in `messages/<locale>.overrides.json`, which the
script never overwrites), and `lib/market.ts` still formats money with a
hardcoded `en-US`  deliberate, since changing decimal separators touches
amount parsing as well as display.

Also fixed en route: the homepage no longer claims "seven core digital assets",
and the FAQ no longer hardcodes the old asset list  both were stale since the
catalogue became admin-managed.

## Original plan

## Context

The client wants the site available in other languages, including Arabic. Today
there is no internationalisation at all: `<html lang="en">` is hardcoded, there
is no `dir` attribute, and every user-facing string is written inline in JSX
across 21 pages (~5,400 lines).

**This is site localisation, not a translation widget.** A language picker
switches the whole interface  nav, buttons, dashboard, forms  into the chosen
language.

### Translation engine: DeepL, called once per language

DeepL generates the translations via a **one-off script**, not on every page
view. English text is extracted to `messages/en.json`, the script sends it to
DeepL, and the returned Arabic/French/Spanish are written to their own files.
Visitors then just load a JSON file  **no API call ever happens from live
traffic**, so there's no per-visitor cost and no dependency on DeepL being up.

| | |
| --- | --- |
| Engine | **DeepL API** (`AR`, `FR`, `ES` targets) |
| When it runs | A script, on demand  when text changes or a language is added |
| Runtime cost | **None.** The app reads local JSON |
| Volume | Site is ~30,000 chars; all three languages ≈ 90,000 chars total |
| DeepL API Free allowance | 500,000 chars/month  the whole job fits several times over |

**Arabic is supported.** DeepL added it in 2024 (Modern Standard Arabic, which
is the right register for financial copy). It's recent enough to be worth
confirming on your tier when you sign up. Note DeepL covers ~30 languages, not
Google's ~130  fine for this list, but a constraint if an unusual language is
requested later.

**Google was considered and dropped**: its free embeddable website widget has
been discontinued, and the Cloud Translation API requires a billing account.

Two caveats that follow:

1. **Quality.** Interface labels ("Deposit", "Portfolio overview") will be
   fine. **Legal and risk wording must be reviewed by a native speaker before
   going live**  a mistranslated volatility disclaimer is a liability, not a
   cosmetic bug. DeepL is generally strong on French and Spanish; Arabic is its
   newest language and deserves the closest review.
2. **Output is editable.** The generated files are plain JSON in the repo. Any
   correction is a one-line edit, and the script won't clobber it  see the
   override rule below.

### Decisions made

- **Scope**: everything a customer sees  marketing pages *and* the signed-in
  dashboard. The **admin panel stays English**, since only staff use it.
- **Languages**: English, Arabic, French, Spanish. Adding another is one script run.
- **URLs**: path-based  `/en/about`, `/ar/dashboard`. Arabic pages get real,
  shareable, indexable URLs, and every marketing page stays statically
  prerendered (preserving the Phase 4 performance work).
- **RTL**: full mirroring for Arabic, not just text direction.

### What the codebase forces

- **22 of 33** page/layout files are `"use client"`, so the solution must work
  in client components, not just server ones.
- Text is deeply inline, including strings wrapping JSX  e.g. an `<h1>`
  containing `<span className="text-gradient-gold">held to institutional
  standards</span>`. Those need rich-text translation, not plain strings.
- **~199 direction-specific utilities** (`ml-`, `pr-`, `text-right`,
  `rounded-l`, `border-l`, `left-`…) across `app/` and `components/`.
- Fonts are **Inter + IBM Plex Mono  neither has Arabic glyphs.**

## Approach

Use **`next-intl`**, the standard i18n library for the Next.js App Router. It
handles server *and* client components, locale routing, and rich text with
embedded JSX  all three of which this codebase needs.

### 1. Restructure routes under `app/[locale]/`

Everything except the true root files moves:

```
app/layout.tsx                    (stays  html/body shell)
app/[locale]/layout.tsx           (new  sets lang + dir, provides messages)
app/[locale]/page.tsx             ← app/page.tsx
app/[locale]/about/…              ← app/about/…
app/[locale]/(authenticated)/…    ← app/(authenticated)/…
…and so on for all 21 pages
```

Mechanical but large. `error.tsx`, `global-error.tsx` and `not-found.tsx` keep
their existing three-way structure.

Add `middleware.ts` for locale detection and redirecting bare `/` to the best
match from the `Accept-Language` header, defaulting to English.

### 2. Extract strings into message catalogues

`frontend/messages/{en,ar,fr,es}.json`, namespaced per page/area:

```json
{ "home": { "heroTitle": "Digital asset wealth management…" },
  "wallets": { "deposit": "Deposit", "withdraw": "Withdraw" } }
```

Components call `useTranslations("wallets")` (client) or `getTranslations`
(server). Strings containing JSX use next-intl's rich-text form so the markup
stays in the component and only the words live in the file.

`en.json` is hand-written as the single source of truth; the other three are
generated from it.

### 3. The DeepL translation script

`frontend/scripts/translate.ts`, run with
`pnpm --filter frontend translate [locale]`:

1. Reads `messages/en.json`.
2. Diffs against the existing target file and **sends only new or changed
   keys**  so a re-run after editing one sentence costs a handful of
   characters, not the whole site.
3. Batches strings into few requests (DeepL accepts arrays), targets `AR`/`FR`/`ES`.
4. Writes the result back, preserving key order for readable diffs.

Two rules that keep it safe to re-run:

- **`tag_handling: "xml"`** so next-intl's rich-text placeholders (`<b>`,
  `{amount}`) survive translation instead of being mangled or translated.
- **Manual overrides are never overwritten.** Any key listed in
  `messages/<locale>.overrides.json` is left alone, so a native speaker's
  correction to a risk disclaimer survives the next script run. This matters 
  without it, the first re-run silently reverts every human fix.

`DEEPL_API_KEY` lives in `frontend/.env` (added to `.env.example`, never
committed). The key is only ever read by this script  it is not bundled into
the app and no runtime code touches DeepL.

### 4. Right-to-left support

- `app/[locale]/layout.tsx` sets `<html lang={locale} dir={locale === "ar" ? "rtl" : "ltr"}>`.
- Convert direction-specific utilities to logical ones  `ml-`→`ms-`,
  `mr-`→`me-`, `pl-`→`ps-`, `pr-`→`pe-`, `text-left`→`text-start`,
  `text-right`→`text-end`, `border-l`→`border-s`, `rounded-l`→`rounded-s`,
  `left-`→`start-`, `right-`→`end-`. Tailwind v4 supports all of these natively
  and they're no-ops in LTR, so English is unaffected.
- Icons that imply direction (`ArrowRight`, `ArrowLeft`, the sidebar chevrons)
  need flipping under RTL.
- Leave `components/ui/*` primitives alone unless a screen visibly breaks 
  they're generated shadcn code and most of their `left-`/`right-` usage is
  dropdown positioning that Radix already handles.

### 5. Arabic font

Add **Noto Sans Arabic** (Google Fonts, same `<link>` already in
`app/layout.tsx`) and set it ahead of Inter in `--font-sans` when the locale is
Arabic. Numerals stay Western digits, matching the existing `num` utility used
for balances.

### 6. Language switcher

A small `LanguageSwitcher` component in the marketing header and the dashboard
sidebar. Switching navigates to the same route under the new locale prefix
(`/en/wallets` → `/ar/wallets`) so the user stays where they are.

### 7. Formatting

`formatUsd` / `formatCryptoAmount` / `formatPercent` in `lib/market.ts` and the
`date-fns` calls currently hardcode `en-US`. Pass the active locale so numbers
and dates render correctly per language. **Money stays in USD**  this is
translation, not currency conversion.

## Deliberately out of scope

- **The admin panel** stays English (per the scope decision).
- **Database content**  currency names an admin types, transaction notes, KYC
  fields  is stored in one language and is *not* translated. Only the app's own
  interface is. Worth confirming that matches expectations for currency names.
- **Currency conversion.** Prices remain USD in every language.

## Critical files

- `frontend/src/app/layout.tsx`  html shell, fonts
- `frontend/src/app/[locale]/layout.tsx`  new; `lang`/`dir`, message provider
- `frontend/middleware.ts`  new; locale detection and redirects
- `frontend/messages/{en,ar,fr,es}.json`  new; the catalogues
- `frontend/scripts/translate.ts`  new; the DeepL generation script
- `frontend/.env.example`  new `DEEPL_API_KEY` entry
- `frontend/src/lib/market.ts`  locale-aware number formatting
- `frontend/src/components/site/SiteHeader.tsx`, `dashboard/layout.tsx`  switcher placement
- Every page under `app/[locale]/`  string extraction

## Prerequisite from you

A **DeepL API key** (Free tier is enough) in `frontend/.env` as
`DEEPL_API_KEY=…`. I'll build everything to read it from there and never handle
the credential directly. If the key isn't ready, the work can still land with
`en.json` complete and the other locales generated later  the app just falls
back to English for any missing key.
